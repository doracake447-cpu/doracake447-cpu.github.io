1) Fundamentals Concepts

An Operating System is a resource manager that provides abstractions over hardware and enables safe, efficient program execution. Think of it as the layer that lets dozens of programs believe they each own the whole machine, while in reality the OS is constantly time-slicing the CPU, partitioning memory, and mediating access to disks and network cards behind the scenes.

Kernel mode vs user mode

Every CPU that runs a modern OS has at least two privilege levels. Kernel mode (also called supervisor or ring 0) can execute any instruction, including ones that touch the memory-management unit, disable interrupts, or talk directly to a disk controller. User mode (ring 3) is deliberately crippled — it can do arithmetic, read/write its own memory, and call approved entry points into the kernel, but nothing more.

Example Suppose a buggy game tries to write directly to video memory to draw a frame faster, bypassing the graphics driver. In user mode, that raw memory address isn't mapped into the game's address space, so the CPU raises a protection fault and the OS kills the process (or the game crashes with a segfault) instead of corrupting another program's display buffer or the kernel itself. If user code could freely issue privileged instructions, one careless or malicious program could take down the entire machine.

System calls

A system call is the sanctioned doorway from user mode into kernel mode. You never enter the kernel by jumping to an arbitrary address — you execute a special trap instruction, the CPU switches privilege levels at a fixed, kernel-controlled entry point, and the kernel decides what to do based on a syscall number you passed in a register.

Example When your C program calls printf("hello\n"), most of that work happens entirely in user space — formatting the string, buffering it. Only when the buffer is flushed does libc issue a write() system call, trapping into the kernel so the kernel (which owns the actual terminal device) can copy those bytes out to the screen. That's why printf feels instant even though "writing to the screen" is technically a kernel-mediated operation — most calls just fill a user-space buffer and no trap happens at all.

Interrupts vs traps/exceptions

Both interrupts and traps divert the CPU away from whatever it was doing, but the trigger is different. An interrupt comes from outside the currently running instruction stream — a keyboard press, a network packet arriving, or a timer chip firing — and can happen at essentially any point in a program's execution. A trap (or exception) is caused directly by the instruction the CPU is executing right now, so it's synchronous and reproducible.

Example Two events feel similar but are handled differently: (1) you press a key while a video is playing — a hardware interrupt fires, the CPU finishes its current instruction, saves state, and jumps to the keyboard interrupt handler, then resumes the video exactly where it left off. (2) The video player divides a duration by a variable that happens to be zero — a trap fires immediately, caused by that exact instruction; re-running the same code with the same input will trap again every time, unlike an interrupt which depends on external timing.

Context switch

A context switch is the act of saving one task's CPU state (registers, program counter, stack pointer) and loading another's, so the CPU can run a different process or thread. It is pure bookkeeping overhead — no application instructions execute during the switch itself — which is exactly why an OS tries to minimize how often it happens relative to useful work done.

Interview tip: Explain that user mode improves security and stability by preventing applications from directly issuing privileged instructions — the kernel is the only trusted arbiter of shared hardware. If pressed for an example, use the printf/write() trace above; it shows you understand where the user/kernel boundary actually sits in code you write every day.

2) Boot Process & System Calls — fork()/exec() Explained Concepts + Code

Simplified boot sequence

Booting is the process of going from "powered off" to "a shell waiting for your command," and it happens in clearly separated stages, each handing off to the next:

  1. Firmware (BIOS/UEFI): the very first code that runs. It does a power-on self-test (checks RAM, detects the keyboard, etc.), then looks at a fixed location on a bootable device for the next-stage loader.
  2. Bootloader (e.g. GRUB): a small program whose only job is to find the kernel image on disk, load it into memory, and jump to its entry point. It may also load an initial RAM disk with just enough drivers to mount the real root file system.
  3. Kernel init: the kernel sets up its own memory management, interrupt vector table, and device drivers, then mounts the root file system so the rest of the OS's files become accessible.
  4. Init process (PID 1, e.g. systemd/init): the very first user-space process, spawned directly by the kernel. Everything else you ever run — your shell, your browser, this very page's server if applicable — is a descendant of PID 1.

fork() and exec() — how new programs actually start

On Unix-like systems there is no single "run this program" system call. Instead, starting a new program is deliberately split into two independent steps, which gives a lot of flexibility: fork() creates a new process that is an exact copy of the caller, and exec() replaces a process's memory image with a different program entirely. Combining them lets the parent do setup work (like redirecting output) in the child before the new program actually starts running.

Analogy Imagine you're a chef (the parent process) and you want an assistant to go cook a completely different dish. fork() is like cloning yourself — the clone has your exact memory, your exact kitchen station, your exact half-finished task. exec() is the clone then throwing away everything it was doing and instead becoming a dedicated pasta-making robot, keeping only its physical station (the process ID, open file handles) but with entirely new instructions (a new program) loaded in.
Example — what happens when you type ls -l in a shell
  1. The shell (say, bash) is sitting in a loop reading your input. You type ls -l and press enter.
  2. Bash calls fork(). The kernel creates a new process that is a near-identical copy of bash — same open files, same environment variables, same code loaded in memory. At this instant there are two processes both running the bash program.
  3. fork() returns twice — once in each process — but with a different value: it returns the child's PID (a positive number) to the parent, and 0 to the child. This is the only way the two now-identical processes can tell which one they are.
  4. The child process checks "did I get 0 back?" — yes — so it calls exec("ls", ["-l"]). This throws away the bash program image inside that child process and loads the ls binary in its place, starting it fresh at ls's main(). The process ID doesn't change, but everything the process was running does.
  5. Meanwhile the parent bash process checked "did I get a positive PID back?" — yes — so it calls wait(), pausing itself until that child (now running as ls) finishes and produces output.
  6. ls prints the directory listing, then exits. The kernel wakes the parent bash back up, hands it the child's exit status, and bash prints a fresh prompt for your next command.
fork() + exec() + wait() — the classic process-creation patternC
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    pid_t pid = fork();  // duplicates the calling process (copy-on-write)

    if (pid < 0) {
        perror("fork failed");
        return 1;
    } else if (pid == 0) {
        // We are the CHILD: fork() returned 0 here.
        execlp("ls", "ls", "-l", NULL); // replaces this process's image with ls
        perror("exec failed");  // only reached if exec itself fails to launch
        _exit(1);
    } else {
        // We are the PARENT: fork() returned the child's PID here.
        int status;
        waitpid(pid, &status, 0);  // block until the child (now running ls) finishes
        printf("child exited with %d\n", WEXITSTATUS(status));
    }
    return 0;
}
Why it's structured this way: because fork() and exec() are separate calls, the child gets a window to modify its own environment — redirecting stdout to a file, changing its working directory, dropping privileges — before calling exec(), without the parent needing to know any of the new program's internals. This is exactly how shell features like ls -l > out.txt are implemented: the child reopens file descriptor 1 to point at out.txt between the fork and the exec.

Copy-on-write (COW): modern fork() does not physically duplicate the parent's memory up front — that would be wasteful if the child is about to call exec() and discard it all anyway. Instead, both processes share the same physical memory pages, marked read-only. Only if either process later writes to a shared page does the kernel copy just that one page, so the two can diverge. In the ls example above, the child never writes to the inherited memory before calling exec(), so in practice almost no copying happens at all.

3) Process vs Thread Concepts

A process is a running program together with everything it needs to execute independently: its own virtual address space, open file descriptors, and a process control block tracked by the kernel. A thread is a unit of execution within a process — it has its own stack and register state, but shares the process's address space, heap, and open files with every other thread in that same process.

PropertyProcessThread
Address spaceSeparateShared inside same process
Creation costHigherLower
CommunicationIPC neededShared memory naturally
Fault isolationStrongWeak (thread crash may kill process)
Example Your web browser is one process. Each tab is often implemented as a separate process deliberately — so a crashing or hung tab can be killed without taking down the rest of your browser, and a compromised tab can't directly read another tab's memory. Inside a single tab's process, however, rendering, JavaScript execution, and networking may run as multiple threads that share the tab's data — because they legitimately need to cooperate closely and passing that much data through IPC on every frame would be far too slow.

PCB (Process Control Block) stores PID, state, registers, program counter, scheduling info, memory pointers, open file table.

Thread states: new, ready, running, blocked/waiting, terminated.

Concurrency vs Parallelism: concurrency is about structure — multiple tasks make progress in overlapping time periods, potentially by interleaving on a single core. Parallelism is about execution — tasks genuinely run at the same instant on different cores. A single-core machine running a time-sliced scheduler gives you concurrency without parallelism; a multi-core machine running one thread per core gives you both.

Creating two threads with POSIX pthreadsC
#include <stdio.h>
#include <pthread.h>

void *worker(void *arg) {
    int id = *(int *)arg;
    printf("thread %d running\n", id);
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    int a = 1, b = 2;

    pthread_create(&t1, NULL, worker, &a); // shares heap/globals with main
    pthread_create(&t2, NULL, worker, &b);

    pthread_join(t1, NULL);  // block until t1 finishes
    pthread_join(t2, NULL);
    return 0;
}
Note the difference from fork(): here there is only ever one address space. Both t1 and t2 can read and write the same global variables directly — no pipe, no shared-memory segment needed — which is exactly why threads need explicit synchronization (covered next) to avoid stepping on each other.

4) Inter-Process Communication Concepts + Code

Because separate processes do not share memory (unlike threads), the OS must provide explicit channels for them to exchange data when they need to cooperate. Which mechanism you pick depends on whether the processes are related, on the same machine, and how much data needs to move.

  • Pipes: a unidirectional byte stream between related processes (typically parent/child), implemented as an in-kernel buffer with a read end and a write end.
  • Named pipes (FIFOs): behave like pipes but have a path in the file system, so even unrelated processes can open the same FIFO and communicate.
  • Shared memory: the fastest IPC mechanism — a region of physical memory mapped into multiple processes' address spaces so they can read/write it like ordinary variables, with no kernel copying on each access. It needs external synchronization since the kernel does not serialize accesses for you.
  • Message queues: a kernel-managed queue of discrete, typed messages — useful when you want structured, ordered communication without managing your own buffer.
  • Sockets: work across machines over a network, not just between processes on the same host.
  • Signals: a lightweight, asynchronous notification of an event (e.g. SIGKILL to terminate, SIGCHLD when a child exits) — carries almost no data, just "this event happened."
Example — the shell pipeline ls | grep txt When you run ls | grep txt, your shell creates a pipe, then forks twice. In the first child, it duplicates the pipe's write end onto file descriptor 1 (stdout) and execs ls — so anything ls "prints" actually flows into the pipe instead of your terminal. In the second child, it duplicates the pipe's read end onto file descriptor 0 (stdin) and execs grep txt — so grep reads ls's output as if it were typed input. Neither ls nor grep was written with any awareness of the other; the shell wires them together purely through this kernel-managed pipe.
Anonymous pipe between parent and childC
#include <stdio.h>
#include <unistd.h>
#include <string.h>

int main(void) {
    int fd[2];
    pipe(fd);                 // fd[0] = read end, fd[1] = write end

    if (fork() == 0) {
        close(fd[0]);         // child only writes, so close the read end
        write(fd[1], "hi parent", 9);
        close(fd[1]);
    } else {
        char buf[16] = {0};
        close(fd[1]);         // parent only reads, so close the write end
        read(fd[0], buf, sizeof(buf));
        printf("parent got: %s\n", buf);
        close(fd[0]);
    }
    return 0;
}
Why close the unused end: both ends are inherited by the child across fork(). Closing the end you don't need is not just tidy — for a real pipeline it's what lets read() return end-of-file once the writer is truly done, since the kernel only signals EOF when every copy of the write end has been closed.
Interview tip: If asked "fastest IPC mechanism", say shared memory — but immediately add the caveat that it trades safety for speed since the OS does not serialize access; you must add your own mutex/semaphore, exactly like coordinating threads.

5) CPU Scheduling Concepts + Numericals

When more processes are ready to run than there are CPU cores, the OS scheduler decides who runs next and for how long. The goal is to balance several competing metrics: maximize CPU utilization and throughput (jobs completed per unit time), while minimizing waiting time, turnaround time, and response time (especially important for interactive programs where a user is staring at the screen).

AlgorithmTypeProsCons
FCFSNon-preemptiveSimple, fair by arrivalConvoy effect, poor response

Formula reminders:

Turnaround = Completion − Arrival Waiting = Turnaround − Burst Response = FirstRun − Arrival
Analogy Think of a single checkout counter at a grocery store. FCFS is a strict single-file line — fair, but if the person at the front has a full cart, everyone behind them waits, even if they only have two items (the "convoy effect"). Round Robin is more like the cashier giving everyone at most 4 items' worth of scanning before moving to the next person in line, cycling back around — nobody with a small cart waits long, but the cashier does more start-stop switching overall.
Worked example — FCFS: Processes P1(burst 5, arrival 0), P2(burst 3, arrival 1), P3(burst 8, arrival 2).
Execution order by arrival: P1 runs 0–5, P2 runs 5–8, P3 runs 8–16.
Waiting: P1 = 0, P2 = 5−1 = 4, P3 = 8−2 = 6. Average waiting = (0+4+6)/3 = 3.33.
Round Robin simulator (quantum-based)Python
from collections import deque

def round_robin(burst, quantum):
    n = len(burst)
    remaining = list(burst)
    queue = deque(range(n))
    t = 0
    waiting = [0] * n
    last_run = [0] * n

    while queue:
        i = queue.popleft()
        run = min(quantum, remaining[i])
        waiting[i] += t - last_run[i]
        t += run
        remaining[i] -= run
        last_run[i] = t
        if remaining[i] > 0:
            queue.append(i)   # not done — go to back of the ready queue

    return waiting

# burst times for P1, P2, P3; quantum = 4
print(round_robin([10, 5, 8], 4))
Reading the code: every time a process is popped, it runs for at most quantum units. If it still has work left, it goes to the back of the queue rather than continuing — this is exactly what makes RR preemptive and fair to short jobs, at the cost of extra context switches versus FCFS.
Interview tip: If asked about RR quantum size, explain: too small means heavy context-switch overhead approaching processor-sharing; too large behaves like FCFS and hurts interactive response.

6) Synchronization & Critical Section Concepts + Code

Race condition: a bug where the final outcome of concurrent operations depends on the unpredictable order in which they happen to be interleaved by the scheduler — the same code can produce different results on different runs.

Example — a race condition on a shared bank balance Two threads both run balance = balance + 100 on a shared account starting at 500. That single line actually takes three CPU steps: read balance into a register, add 100, write the register back to balance. If thread A reads 500, then gets paused before writing back, and thread B also reads 500, adds 100, and writes 600 — when A resumes it still has the stale value 500 in its register, adds 100, and writes 600 again. Two deposits of 100 happened, but the balance only reflects one. This is exactly the kind of bug a critical section protects against.

Critical-section solution requirements:

  • Mutual exclusion: only one process/thread in the critical section at a time.
  • Progress: selection of who enters next cannot be postponed indefinitely.
  • Bounded waiting: a limit exists on how many times others enter before a waiting process gets its turn.

Mechanisms

  • Mutex: lock/unlock primitive for exclusive access; has ownership — the thread that locks must be the one to unlock.
  • Semaphore: integer counter with atomic wait()/signal() (a.k.a. P/V); binary (0/1) or counting.
  • Monitor + condition variables: a higher-level structured construct that bundles a lock with wait/notify, common in languages like Java.
  • Spinlock: a lock where a waiting thread busy-loops checking a flag instead of sleeping; only sensible for very short critical sections on multiprocessors, since sleeping/waking a thread has overhead that can exceed the wait itself.
Mutex-protected shared counter (fixes the balance race above)C / pthreads
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
long counter = 0;

void *increment(void *arg) {
    for (int i = 0; i < 100000; i++) {
        pthread_mutex_lock(&lock);    // enter critical section — blocks if another thread is inside
        counter++;                        // now safe: only one thread can be here at a time
        pthread_mutex_unlock(&lock);  // leave critical section, wake a waiter if any
    }
    return NULL;
}
Without the lock, two threads both running this loop would lose increments exactly like the bank balance example — with it, every increment is guaranteed to see the previous thread's write before making its own.
Counting semaphore — limiting concurrent accessC / POSIX semaphores
#include <semaphore.h>

sem_t pool;               // e.g. limit to 3 concurrent DB connections
sem_init(&pool, 0, 3);   // 0 = shared between threads, initial count = 3

void use_resource(void) {
    sem_wait(&pool);      // P(): decrement; blocks if count == 0 (pool exhausted)
    // ... use one of the 3 limited connections ...
    sem_post(&pool);      // V(): increment; wakes a waiter if any are blocked
}
Unlike the mutex example, this isn't about exclusive access to one thing — up to three threads can hold the semaphore simultaneously, which is why a counting semaphore is the right tool for "limit concurrency to N", not just "allow only one at a time".
Difference: Mutex has ownership (the thread that locks must unlock). Semaphore generally does not enforce ownership — any thread can signal — which is why semaphores are also used for signaling between threads, not just exclusion.

7) Classic Synchronization Problems Code

These three appear constantly in interviews because each teaches a different synchronization pattern. Know the shared state involved and exactly where each semaphore/lock goes, not just the final code.

Producer–Consumer (bounded buffer)

Analogy Think of a small conveyor belt with only 10 slots between a baker (producer) and a shop counter (consumer). The baker must stop if all 10 slots are full — there's nowhere to put the next loaf. The shop clerk must stop if all slots are empty — there's nothing to sell yet. empty counts free slots, full counts loaves waiting, and the mutex makes sure the baker and clerk never fumble the same slot at once.
Producer-Consumer with counting semaphoresC-like pseudocode
int BUF_SIZE = 10;
sem_t empty, full;      // counts free slots / filled slots
pthread_mutex_t mutex;  // protects the buffer itself

sem_init(&empty, 0, BUF_SIZE); // starts full of empty slots
sem_init(&full,  0, 0);        // starts with zero items

producer() {
    while (1) {
        item = produce_item();
        sem_wait(&empty);          // wait for a free slot (blocks the baker if belt is full)
        pthread_mutex_lock(&mutex);
        insert_into_buffer(item);
        pthread_mutex_unlock(&mutex);
        sem_post(&full);           // signal an item is available
    }
}

consumer() {
    while (1) {
        sem_wait(&full);            // wait for an item (blocks the clerk if belt is empty)
        pthread_mutex_lock(&mutex);
        item = remove_from_buffer();
        pthread_mutex_unlock(&mutex);
        sem_post(&empty);          // signal a free slot
        consume_item(item);
    }
}

Readers–Writers (readers-preference variant)

Analogy A library reading room: many people can read the same reference book on the shelf simultaneously without conflict, but if a librarian wants to update the book's contents, everyone else must step out first, and no one else can walk in until the update is done.
Readers-Writers with a read countC-like pseudocode
int read_count = 0;
pthread_mutex_t rc_lock;   // protects read_count
sem_t rw_lock;             // binary: exclusive access for a writer

reader() {
    pthread_mutex_lock(&rc_lock);
    read_count++;
    if (read_count == 1) sem_wait(&rw_lock); // first reader locks out writers
    pthread_mutex_unlock(&rc_lock);

    read_data();

    pthread_mutex_lock(&rc_lock);
    read_count--;
    if (read_count == 0) sem_post(&rw_lock); // last reader unlocks writers
    pthread_mutex_unlock(&rc_lock);
}

writer() {
    sem_wait(&rw_lock);   // exclusive access, just like a normal mutex
    write_data();
    sem_post(&rw_lock);
}
Why read_count needs its own lock: only the first reader to arrive should lock out writers, and only the last reader to leave should let writers back in — everyone in between just reads freely. Tracking "am I first/last" safely requires read_count itself to be protected from simultaneous updates by multiple readers.

Dining Philosophers (deadlock-safe: asymmetric ordering)

Analogy Five philosophers sit around a circular table with one fork between each pair — five forks total — and each needs both neighboring forks to eat. If everyone picks up their left fork at the same instant, every fork is taken and everyone waits forever for their right fork: a deadlock. Breaking the symmetry — say, the philosopher with the lowest ID always reaches for their lower-numbered fork first — guarantees at least one philosopher can always get both forks and eat.
Avoid circular wait by picking up the lower-numbered fork firstC-like pseudocode
// N forks/philosophers around a table; classic deadlock if everyone
// grabs their left fork first. Fix: break circular wait by ordering.
philosopher(int i) {
    int first  = min(i, (i + 1) % N);
    int second = max(i, (i + 1) % N);

    sem_wait(&fork[first]);   // always take the lower-numbered fork first
    sem_wait(&fork[second]);
    eat();
    sem_post(&fork[second]);
    sem_post(&fork[first]);
}
Interview tip: For dining philosophers, naming the fix ("break the circular-wait condition via a resource ordering") is worth more than reciting the code — it shows you understand why it prevents deadlock, not just that it does.

8) Deadlocks Concepts + Code

Deadlock: a set of processes are permanently blocked, each waiting for a resource held by another process in the same set, so none of them can ever make progress.

Analogy Two cars meet nose-to-nose in a single-lane alley with no room to pass. Car A needs the space Car B occupies to move forward, and Car B needs the space Car A occupies. Neither will voluntarily give up its spot ("no preemption") and each is holding its position while waiting on the other ("hold and wait") — that's a deadlock. In dining philosophers above, forks play the role of the alley: every philosopher holding one fork while waiting for another is the same standoff.

Coffman conditions (all four required simultaneously for deadlock to occur):

  • Mutual exclusion: at least one resource must be held in a non-shareable way.
  • Hold and wait: a process holds one resource while waiting for another.
  • No preemption: resources can't be forcibly taken away; they must be released voluntarily.
  • Circular wait: a cycle exists in the "waiting for" graph among the processes.

Handling strategies:

StrategyIdeaExample
PreventionBreak one Coffman conditionResource ordering to avoid circular wait
AvoidanceAllocate only if the resulting state is safeBanker's algorithm
Detection + RecoveryAllow deadlock, detect cycle, recoverKill a process / preempt a resource
IgnoreAssume rare, restart if it happensMost general-purpose OSes (the "ostrich algorithm")

The Banker's algorithm avoids deadlock by simulating: before granting a resource request, it pretends to grant it and checks whether every process could still finish given enough time, assuming each only ever asks for up to its declared maximum. If such a completion order exists, the state is "safe" and the request is actually granted; otherwise the process is made to wait, even if the resource is currently free.

Banker's Algorithm — safety checkPython
def is_safe(available, max_need, allocation):
    n_procs = len(allocation)
    n_res = len(available)
    need = [[max_need[i][j] - allocation[i][j] for j in range(n_res)]
            for i in range(n_procs)]

    work = list(available)
    finished = [False] * n_procs
    safe_sequence = []

    for _ in range(n_procs):
        for i in range(n_procs):
            if not finished[i] and all(need[i][j] <= work[j] for j in range(n_res)):
                # process i can finish with what's currently available
                work = [work[j] + allocation[i][j] for j in range(n_res)]
                finished[i] = True
                safe_sequence.append(i)
                break

    return (all(finished), safe_sequence)

# Example: 3 processes, 3 resource types (A, B, C)
available   = [3, 3, 2]
max_need    = [[7,5,3], [3,2,2], [9,0,2]]
allocation  = [[0,1,0], [2,0,0], [3,0,2]]

print(is_safe(available, max_need, allocation))
# -> (True, [1, 0, 2])  — a safe sequence exists
How to reason about it out loud: at each step, find any process whose remaining need (max minus what it already holds) can be satisfied by what's currently available. Let it finish and release its resources back into available, then repeat with the larger pool. If every process eventually finishes this way, the state is safe — in the example, process 1 needs at most (3−2, 2−0, 2−0) = (1,2,2), which fits in the available (3,3,2), so it can go first and free up (2,0,0) more.

9) Memory Management Concepts + Worked Example

Contiguous allocation gives each process one unbroken chunk of physical memory. Over time, as processes come and go, this leaves gaps between allocations that are individually too small to satisfy new requests — external fragmentation — even though the total free memory might be plenty. Paging solves this by allocating memory in fixed-size chunks that don't need to be contiguous at all.

Paging: logical (virtual) memory is split into fixed-size pages; physical memory is split into frames of the same size. A logical address is really two parts: a page number and an offset within that page. The OS maintains a page table per process mapping page numbers to physical frame numbers.

Segmentation: instead of fixed-size chunks, memory is divided by logical units that make sense to the programmer — code, data, stack — each with its own base and limit register. This maps more naturally to how programs are structured, but reintroduces external fragmentation since segments vary in size.

Fragmentation summary:

  • Internal fragmentation: wasted space inside an allocated unit — e.g. a process needing 4097 bytes still gets two full 4 KB pages, wasting almost an entire page.
  • External fragmentation: free memory exists in total but is scattered in chunks too small individually to satisfy a request — the classic problem with contiguous/segmented allocation, avoided by paging.

Because every memory access would otherwise require an extra lookup into the page table (itself sitting in memory), hardware provides the TLB (Translation Lookaside Buffer) — a small, very fast cache of recently used page-table entries right next to the CPU, so most translations skip the full page-table walk entirely.

Worked address translation: page size = 4 KB (212), so the low 12 bits of a virtual address are the offset (they identify a byte within a page) and the remaining high bits are the page number (they identify which page).
Virtual address 0x2050 → page number = 0x2050 >> 12 = 2, offset = 0x2050 & 0xFFF = 0x050.
If the page table says "page 2 lives in frame 7", physical address = (7 << 12) | 0x050 = 0x7050 — same offset, different base, because the offset within a page never changes during translation, only which physical page it lands in.
Virtual → physical address translationPython
def translate(vaddr, page_table, page_size=4096):
    offset_bits = page_size.bit_length() - 1
    page_number = vaddr >> offset_bits
    offset = vaddr & (page_size - 1)

    if page_number not in page_table:
        raise Exception("Page fault: page not resident")

    frame_number = page_table[page_number]
    return (frame_number << offset_bits) | offset

page_table = {0: 5, 1: 9, 2: 7}
print(hex(translate(0x2050, page_table)))  # -> 0x7050

10) Virtual Memory & Page Replacement Concepts + Code

Virtual memory lets a process behave as if it has more memory than physically exists, by keeping only the pages it's actively using resident in RAM and leaving the rest on disk until needed — this is called demand paging.

Page fault handling: when a process touches a page that isn't currently in RAM, the hardware traps into the kernel. The kernel validates that the access is actually legal (not, say, a wild pointer), locates the page's data on disk, loads it into a free physical frame — evicting some other page first if none are free — updates the page table, and finally restarts the very instruction that faulted, which now succeeds because the page is resident.

PolicyRuleNotes
FIFOEvict the oldest loaded pageSimple, but can exhibit Belady's anomaly (more frames → more faults)
LRUEvict the least-recently-used pageGood approximation of optimal, but costly to implement exactly
OptimalEvict the page used farthest in the futureTheoretical benchmark only — needs future knowledge
Clock / Second-chanceUse a reference bit to approximate LRU cheaplyPractical choice in real systems
Worked example — FIFO with 3 frames: reference string 1 2 3 4 1 2 5.
1,2,3 load into the three empty frames — 3 faults, frames now hold [1,2,3] in load order. Referencing 4: not resident, evict the oldest (1) — fault, frames now [2,3,4]. Referencing 1 again: not resident (just evicted!), evict the oldest (2) — fault, frames now [3,4,1]. Referencing 2 again: not resident, evict 3 — fault, frames now [4,1,2]. Referencing 5: not resident, evict 4 — fault.
Total faults = 7 out of 7 references — FIFO evicted pages right before they were needed again here, which is exactly the kind of bad case LRU is designed to avoid.
LRU page replacement simulatorPython
def lru(pages, n_frames):
    frames = []
    faults = 0
    for p in pages:
        if p in frames:
            frames.remove(p)     # move to "most recently used" end
            frames.append(p)
        else:
            faults += 1
            if len(frames) == n_frames:
                frames.pop(0)     # evict least-recently-used (front of list)
            frames.append(p)
    return faults

print(lru([1,2,3,4,1,2,5], 3))  # -> 6 faults with LRU on the same reference string
On this same reference string LRU faults one fewer time than FIFO — when 1 is re-referenced, LRU evicts whichever of 2/3/4 was used longest ago rather than blindly picking the oldest-loaded page, which happens to keep the right page around slightly longer.

Thrashing: when the number of resident pages per process is too small, processes fault almost every time they touch memory. CPU utilization actually drops even though the system looks "busy," because nearly all the time goes into swapping pages in and out rather than executing instructions. The fix is to reduce the multiprogramming level (fewer processes competing for frames) or use the working-set model / page-fault-frequency control to ensure each process holds enough frames for its active working set.

11) File System & I/O Concepts + Code

A file system maps the logical view a program sees — named files organized into directories — onto the physical reality of blocks scattered across a storage device, and keeps metadata alongside each file: size, owner, permissions, timestamps, and where its data blocks actually live.

  • Allocation methods: contiguous (fast sequential access, but suffers external fragmentation like memory does), linked (no fragmentation, but slow random access since you must follow pointers), indexed (e.g. inodes with direct/indirect blocks — a good middle ground used by most real file systems).
  • Directory structures: single-level (one flat namespace), two-level (one directory per user), tree (arbitrary nesting, what you use daily), acyclic graph (allows shared subdirectories via links, still no cycles).
  • Access control: Unix permissions (rwx for owner/group/other) cover the common case cheaply; ACLs allow finer-grained, per-user rules when that's not enough.
  • I/O methods: programmed I/O (the CPU actively polls the device in a loop until it's ready — simple but wastes CPU cycles), interrupt-driven I/O (the CPU issues a request and moves on to other work, the device raises an interrupt when done), DMA (Direct Memory Access — the device transfers data straight to/from memory without the CPU copying it byte by byte, freeing the CPU almost entirely during large transfers).

Kernel buffering and caching improve throughput by holding recently or frequently used disk blocks in memory, and by batching many small writes into fewer, larger device operations — since a single large transfer is far more efficient than the same data sent as many tiny ones.

Example When you call write() on a regular file, the kernel usually just copies your data into an in-memory buffer (the page cache) and returns immediately — the actual disk write may happen later, batched with other pending writes. That's why write() often feels instantaneous even to a slow disk, and also why an unexpected power loss can lose data that a program "already wrote" but the kernel hadn't yet flushed — which is exactly what calls like fsync() exist to force.
Basic file I/O via syscallsC
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    int fd = open("notes.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) return 1;

    const char *msg = "paging beats segmentation for fragmentation\n";
    write(fd, msg, strlen(msg));  // buffered by the kernel, flushed to disk later
    close(fd);                    // releases the file descriptor
    return 0;
}

12) Disk Scheduling Concepts + Worked Example

A spinning disk has a physical read/write head that must move across cylinders to reach requested data — that seek time dominates disk performance, so the OS reorders pending requests to minimize total head movement rather than serving them in arrival order.

AlgorithmIdea
FCFSServe requests in arrival order — simple but ignores head position entirely
SSTFServe the closest request to the current head position next
SCANSweep head in one direction servicing requests, reverse at the end ("elevator")
C-SCANLike SCAN, but jumps back to the start after reaching the end, servicing only one direction — more uniform wait times
Analogy SSTF behaves like an elevator that always goes to whichever requested floor is nearest, regardless of direction — it minimizes each individual trip but can leave a far-away request waiting a long time if closer requests keep arriving. SCAN behaves like a "real" elevator that sweeps top to bottom and back, picking up everyone along the way in one consistent direction before reversing — less greedy, more predictable worst-case waits.
Worked example — SSTF: head starts at cylinder 50, requests = [98, 183, 37, 122, 14, 124, 65, 67].
Nearest to 50 is 65 → 67 → 37 → 14 → 98 → 122 → 124 → 183.
Total head movement = |50-65| + |65-67| + |67-37| + |37-14| + |14-98| + |98-122| + |122-124| + |124-183| = 15+2+30+23+84+24+2+59 = 239 cylinders.
SSTF total seek distancePython
def sstf(start, requests):
    requests = list(requests)
    head = start
    total = 0
    order = []
    while requests:
        nxt = min(requests, key=lambda r: abs(r - head))
        total += abs(nxt - head)
        head = nxt
        order.append(nxt)
        requests.remove(nxt)
    return order, total

print(sstf(50, [98,183,37,122,14,124,65,67]))

13) High-Frequency Interview Q&A

Q: Why are system calls slower than normal function calls?
A: They require a user-to-kernel mode switch, argument validation, and possibly scheduling or interrupt handling — a normal call is just a jump on the same stack with no privilege change.
Q: Why are threads considered lightweight?
A: They share the process's address space, file descriptors, and other resources, so creation and context-switch overhead is lower than for a full process — no new page tables need to be set up.
Q: Semaphore vs Mutex?
A: Mutex is an ownership-based exclusive lock (only the locker unlocks); semaphore is a more general signaling/counting primitive and often allows a non-owner to signal it — e.g. a consumer thread signaling a producer.
Q: Starvation vs Deadlock?
A: Starvation is indefinite postponement of one process while others keep progressing (e.g. a low-priority job in a priority scheduler with no aging); deadlock is circular waiting where none of the involved processes can proceed at all.
Q: What is a zombie process?
A: A terminated child whose exit status hasn't been collected by its parent yet (parent hasn't called wait()); its PCB lingers in the process table until reaped, purely so the exit status remains available.
Q: What causes priority inversion?
A: A low-priority thread holds a lock needed by a high-priority thread, while an unrelated medium-priority thread preempts the low-priority one and keeps it from ever finishing and releasing the lock — inverting the intended priority order. Mitigate with priority inheritance, which temporarily boosts the lock holder's priority.
Q: What's the difference between a hard link and a symbolic link?
A: A hard link is another directory entry pointing to the same inode (same data, indistinguishable from the "original," and the data survives as long as any hard link exists); a symlink is a separate small file containing a path string, which breaks if the target moves or is deleted.
Q: Why does fork() return twice?
A: It creates a near-identical copy of the calling process; execution resumes in both parent and child right after the call, distinguished only by the return value (0 in the child, the child's PID in the parent, negative on error) — see the worked ls -l walkthrough in section 2 for the full trace.

14) Common Pitfalls to Avoid

  • Confusing concurrency with parallelism — concurrency is about structure (interleaved progress), parallelism is about execution (simultaneous on multiple cores). A single-core machine can be concurrent without ever being parallel.
  • Saying "semaphore = mutex" — they overlap in use but differ in ownership semantics and intended purpose (exclusion vs signaling); a semaphore initialized to 1 can act like a mutex, but a mutex can't easily do everything a counting semaphore can.
  • Forgetting to release locks on early return / exception paths — a common source of deadlock in real code; always match every lock() with an unlock() on every exit path, including error paths.
  • Assuming more page frames always means fewer faults — Belady's anomaly shows FIFO can violate this intuition, faulting more with additional frames for certain reference strings.
  • Ignoring the ABA problem in lock-free code — a value changing from A to B and back to A between a thread's read and its compare-and-swap can fool a naive check into thinking nothing changed.
  • Not reaping child processes — leads to zombie accumulation until the parent exits or calls wait(), slowly consuming process-table entries.
