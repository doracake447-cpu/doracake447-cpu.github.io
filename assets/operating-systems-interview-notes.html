1) Fundamentals Concepts

An Operating System is a resource manager that provides abstractions over hardware and enables safe, efficient program execution. It sits between applications and hardware, multiplexing CPU, memory, storage, and devices among competing programs.

  • Kernel mode vs User mode: privileged instructions (I/O ports, MMU control, halting the CPU) execute only in kernel mode. User processes run in a restricted mode so a bug or malicious program cannot directly touch hardware.
  • System call: a controlled transition from user mode to kernel mode, triggered by a software interrupt/trap instruction (e.g. int 0x80 on old x86 Linux, syscall on x86-64).
  • Interrupt: an asynchronous event (I/O completion, timer tick, device signal) that preempts normal flow regardless of what the CPU is doing.
  • Trap/Exception: a synchronous event caused by the currently executing instruction (e.g. divide-by-zero, illegal opcode, page fault).
  • Context switch: saving and restoring CPU state (registers, program counter, stack pointer, page table pointer) to switch which task the CPU runs; pure overhead — no useful work is done during the switch itself.

How a system call actually flows

  1. User code calls a wrapper (e.g. libc's read()), which loads the syscall number and arguments into registers.
  2. The wrapper executes a trap instruction, raising the privilege level to kernel mode.
  3. The kernel's syscall dispatcher validates arguments and looks up the handler by syscall number.
  4. The handler runs in kernel mode, touching hardware or kernel data structures as needed.
  5. The kernel returns a result and drops the privilege level back to user mode.
Minimal syscall wrapper — x86-64 LinuxC / inline asm
// A tiny illustration of what read()/write() wrappers do under the hood.
// Real libc uses a vDSO/optimized path; this shows the raw mechanism.
long raw_write(int fd, const void *buf, unsigned long count) {
    long ret;
    asm volatile (
        "syscall"
        : "=a"(ret)                    // output: rax holds return value
        : "a"(1),                       // syscall number for write() = 1
          "D"(fd), "S"(buf), "d"(count) // rdi, rsi, rdx = args
        : "rcx", "r11", "memory"   // clobbered by syscall instruction
    );
    return ret;
}
Interview tip: Explain that user mode improves security and stability by preventing applications from directly issuing privileged instructions — the kernel is the only trusted arbiter of shared hardware.

2) Boot Process & System Call Categories Concepts

Simplified boot sequence

  1. Firmware (BIOS/UEFI): runs power-on self-test, initializes basic hardware, locates a bootable device.
  2. Bootloader (e.g. GRUB): loads the kernel image and an initial RAM disk into memory, passes control to the kernel entry point.
  3. Kernel init: sets up memory management, interrupt tables, device drivers, and mounts the root file system.
  4. Init process (PID 1, e.g. systemd/init): starts user-space services and eventually a login/shell.

fork() + exec() + wait() — the classic process-creation patternC
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    pid_t pid = fork();  // duplicates the calling process (copy-on-write)

    if (pid < 0) {
        perror("fork failed");
        return 1;
    } else if (pid == 0) {
        // Child process: pid == 0 here
        execlp("ls", "ls", "-l", NULL); // replaces child's image
        perror("exec failed");  // only reached if exec fails
        _exit(1);
    } else {
        // Parent process: pid is the child's PID
        int status;
        waitpid(pid, &status, 0);  // reap child, avoid a zombie
        printf("child exited with %d\n", WEXITSTATUS(status));
    }
    return 0;
}

Copy-on-write (COW): modern fork() does not physically copy the parent's memory. Both processes share the same physical pages marked read-only; a page is duplicated lazily only when either process writes to it. This makes fork() cheap even for large processes.

3) Process vs Thread Concepts

PropertyProcessThread
Address spaceSeparateShared inside same process
Creation costHigherLower
CommunicationIPC neededShared memory naturally
Fault isolationStrongWeak (thread crash may kill process)

PCB (Process Control Block) stores PID, state, registers, program counter, scheduling info, memory pointers, open file table.

Thread states: new, ready, running, blocked/waiting, terminated.

Concurrency vs Parallelism: concurrency is progress overlap (may still run on one core, interleaved); parallelism is simultaneous execution on multiple cores.

Creating two threads with POSIX pthreadsC
#include <stdio.h>
#include <pthread.h>

void *worker(void *arg) {
    int id = *(int *)arg;
    printf("thread %d running\n", id);
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    int a = 1, b = 2;

    pthread_create(&t1, NULL, worker, &a); // shares heap/globals with main
    pthread_create(&t2, NULL, worker, &b);

    pthread_join(t1, NULL);  // block until t1 finishes
    pthread_join(t2, NULL);
    return 0;
}

4) Inter-Process Communication Concepts + Code

Processes don't share memory by default, so the OS provides IPC mechanisms:

  • Pipes: unidirectional byte stream between related processes (e.g. parent/child).
  • Named pipes (FIFOs): like pipes but have a path in the file system, so unrelated processes can use them.
  • Shared memory: fastest IPC — a memory region mapped into multiple address spaces; needs external synchronization.
  • Message queues: kernel-managed queue of discrete messages.
  • Sockets: works across machines, not just same-host processes.
  • Signals: asynchronous notification of an event (e.g. SIGKILL, SIGCHLD).
Anonymous pipe between parent and childC
#include <stdio.h>
#include <unistd.h>
#include <string.h>

int main(void) {
    int fd[2];
    pipe(fd);                 // fd[0] = read end, fd[1] = write end

    if (fork() == 0) {
        close(fd[0]);         // child only writes
        write(fd[1], "hi parent", 9);
        close(fd[1]);
    } else {
        char buf[16] = {0};
        close(fd[1]);         // parent only reads
        read(fd[0], buf, sizeof(buf));
        printf("parent got: %s\n", buf);
        close(fd[0]);
    }
    return 0;
}
Interview tip: If asked "fastest IPC mechanism", say shared memory — but note it trades safety for speed since the OS does not serialize access; you must add your own mutex/semaphore.

5) CPU Scheduling Concepts + Numericals

Goal: maximize utilization and throughput, while minimizing waiting, turnaround, and response time.

AlgorithmTypeProsCons
FCFSNon-preemptiveSimple, fair by arrivalConvoy effect, poor response
SJFUsually non-preemptiveOptimal avg waiting timeNeeds burst estimate, starvation risk
SRTFPreemptive SJFGood response for short jobsHigh context-switch overhead
PriorityBothSupports importanceStarvation without aging
Round RobinPreemptiveGood interactive responseQuantum tuning sensitive
Multilevel Feedback QueuePreemptiveAdapts to burst behaviorComplex, many tunable params

Formula reminders:

Turnaround = Completion − Arrival Waiting = Turnaround − Burst Response = FirstRun − Arrival
Worked example — FCFS: Processes P1(burst 5, arrival 0), P2(burst 3, arrival 1), P3(burst 8, arrival 2).
Execution order by arrival: P1 runs 0–5, P2 runs 5–8, P3 runs 8–16.
Waiting: P1 = 0, P2 = 5−1 = 4, P3 = 8−2 = 6. Average waiting = (0+4+6)/3 = 3.33.
Round Robin simulator (quantum-based)Python
from collections import deque

def round_robin(burst, quantum):
    n = len(burst)
    remaining = list(burst)
    queue = deque(range(n))
    t = 0
    waiting = [0] * n
    last_run = [0] * n

    while queue:
        i = queue.popleft()
        run = min(quantum, remaining[i])
        waiting[i] += t - last_run[i]
        t += run
        remaining[i] -= run
        last_run[i] = t
        if remaining[i] > 0:
            queue.append(i)   # not done — go to back of the ready queue

    return waiting

# burst times for P1, P2, P3; quantum = 4
print(round_robin([10, 5, 8], 4))
Interview tip: If asked about RR quantum size, explain: too small means heavy context-switch overhead approaching processor-sharing; too large behaves like FCFS and hurts interactive response.

6) Synchronization & Critical Section Concepts + Code

Race condition: output depends on the interleaving of concurrent operations on shared state.

Critical-section solution requirements:

  • Mutual exclusion: only one process/thread in the critical section at a time.
  • Progress: selection of who enters next cannot be postponed indefinitely.
  • Bounded waiting: a limit exists on how many times others enter before a waiting process gets its turn.

Mechanisms

  • Mutex: lock/unlock primitive for exclusive access; has ownership — the locker must unlock.
  • Semaphore: integer counter with atomic wait()/signal() (a.k.a. P/V); binary (0/1) or counting.
  • Monitor + condition variables: a higher-level structured construct that bundles a lock with wait/notify.
  • Spinlock: busy-wait lock; useful only for very short critical sections on multiprocessors, since it wastes CPU while waiting.
Mutex-protected shared counterC / pthreads
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
long counter = 0;

void *increment(void *arg) {
    for (int i = 0; i < 100000; i++) {
        pthread_mutex_lock(&lock);    // enter critical section
        counter++;                        // safe: only one thread here
        pthread_mutex_unlock(&lock);  // leave critical section
    }
    return NULL;
}
Counting semaphore — limiting concurrent accessC / POSIX semaphores
#include <semaphore.h>

sem_t pool;               // e.g. limit to 3 concurrent DB connections
sem_init(&pool, 0, 3);   // 0 = shared between threads, initial count = 3

void use_resource(void) {
    sem_wait(&pool);      // P(): decrement; blocks if count == 0
    // ... use the limited resource ...
    sem_post(&pool);      // V(): increment; wakes a waiter if any
}
Difference: Mutex has ownership (the thread that locks must unlock). Semaphore generally does not enforce ownership — any thread can signal — which is why semaphores are also used for signaling between threads, not just exclusion.

7) Classic Synchronization Problems Code

These three appear constantly in interviews — know the shared state and where each semaphore/lock goes.

Producer–Consumer (bounded buffer)

Producer-Consumer with counting semaphoresC-like pseudocode
int BUF_SIZE = 10;
sem_t empty, full;      // counts free slots / filled slots
pthread_mutex_t mutex;  // protects the buffer itself

sem_init(&empty, 0, BUF_SIZE); // starts full of empty slots
sem_init(&full,  0, 0);        // starts with zero items

producer() {
    while (1) {
        item = produce_item();
        sem_wait(&empty);          // wait for a free slot
        pthread_mutex_lock(&mutex);
        insert_into_buffer(item);
        pthread_mutex_unlock(&mutex);
        sem_post(&full);           // signal an item is available
    }
}

consumer() {
    while (1) {
        sem_wait(&full);            // wait for an item
        pthread_mutex_lock(&mutex);
        item = remove_from_buffer();
        pthread_mutex_unlock(&mutex);
        sem_post(&empty);          // signal a free slot
        consume_item(item);
    }
}

Readers–Writers (readers-preference variant)

Readers-Writers with a read countC-like pseudocode
int read_count = 0;
pthread_mutex_t rc_lock;   // protects read_count
sem_t rw_lock;             // binary: exclusive access for a writer

reader() {
    pthread_mutex_lock(&rc_lock);
    read_count++;
    if (read_count == 1) sem_wait(&rw_lock); // first reader locks out writers
    pthread_mutex_unlock(&rc_lock);

    read_data();

    pthread_mutex_lock(&rc_lock);
    read_count--;
    if (read_count == 0) sem_post(&rw_lock); // last reader unlocks writers
    pthread_mutex_unlock(&rc_lock);
}

writer() {
    sem_wait(&rw_lock);   // exclusive access
    write_data();
    sem_post(&rw_lock);
}

Dining Philosophers (deadlock-safe: asymmetric ordering)

Avoid circular wait by picking up the lower-numbered fork firstC-like pseudocode
// N forks/philosophers around a table; classic deadlock if everyone
// grabs their left fork first. Fix: break circular wait by ordering.
philosopher(int i) {
    int first  = min(i, (i + 1) % N);
    int second = max(i, (i + 1) % N);

    sem_wait(&fork[first]);   // always take the lower-numbered fork first
    sem_wait(&fork[second]);
    eat();
    sem_post(&fork[second]);
    sem_post(&fork[first]);
}
Interview tip: For dining philosophers, naming the fix ("break the circular-wait condition via a resource ordering") is worth more than reciting the code — it shows you understand why it prevents deadlock, not just that it does.

8) Deadlocks Concepts + Code

Deadlock: a set of processes are permanently blocked, each waiting for a resource held by another in the set.

Coffman conditions (all four required simultaneously):

  • Mutual exclusion
  • Hold and wait
  • No preemption
  • Circular wait

Handling strategies:

StrategyIdeaExample
PreventionBreak one Coffman conditionResource ordering to avoid circular wait
AvoidanceAllocate only if the resulting state is safeBanker's algorithm
Detection + RecoveryAllow deadlock, detect cycle, recoverKill a process / preempt a resource
IgnoreAssume rare, restart if it happensMost general-purpose OSes (the "ostrich algorithm")
Banker's Algorithm — safety checkPython
def is_safe(available, max_need, allocation):
    n_procs = len(allocation)
    n_res = len(available)
    need = [[max_need[i][j] - allocation[i][j] for j in range(n_res)]
            for i in range(n_procs)]

    work = list(available)
    finished = [False] * n_procs
    safe_sequence = []

    for _ in range(n_procs):
        for i in range(n_procs):
            if not finished[i] and all(need[i][j] <= work[j] for j in range(n_res)):
                # process i can finish with what's currently available
                work = [work[j] + allocation[i][j] for j in range(n_res)]
                finished[i] = True
                safe_sequence.append(i)
                break

    return (all(finished), safe_sequence)

# Example: 3 processes, 3 resource types (A, B, C)
available   = [3, 3, 2]
max_need    = [[7,5,3], [3,2,2], [9,0,2]]
allocation  = [[0,1,0], [2,0,0], [3,0,2]]

print(is_safe(available, max_need, allocation))
# -> (True, [1, 0, 2])  — a safe sequence exists
How to reason about it out loud: at each step, find any process whose remaining need can be satisfied by what's currently available. Let it finish and release its resources back into available, then repeat. If every process eventually finishes, the state is safe.

9) Memory Management Concepts + Worked Example

Contiguous allocation leads to external fragmentation; paging solves external fragmentation by allocating in fixed-size chunks.

Paging: logical memory is split into pages, physical memory into frames of the same size. A logical address = page number + offset.

Segmentation: memory divided by logical units (code/data/stack), each with a base and limit register.

Fragmentation summary:

  • Internal fragmentation: wasted space inside an allocated block/frame (the last page of a process is rarely full).
  • External fragmentation: free memory exists in total but is scattered in non-contiguous chunks too small individually to satisfy a request.

Page table lookups are accelerated by the TLB (Translation Lookaside Buffer), a small hardware cache of recent page table entries.

Worked address translation: page size = 4 KB (212), so the low 12 bits of a virtual address are the offset and the rest is the page number.
Virtual address 0x2050 → page number = 0x2050 >> 12 = 2, offset = 0x2050 & 0xFFF = 0x050.
If page table says page 2 → frame 7, physical address = (7 << 12) | 0x050 = 0x7050.
Virtual → physical address translationPython
def translate(vaddr, page_table, page_size=4096):
    offset_bits = page_size.bit_length() - 1
    page_number = vaddr >> offset_bits
    offset = vaddr & (page_size - 1)

    if page_number not in page_table:
        raise Exception("Page fault: page not resident")

    frame_number = page_table[page_number]
    return (frame_number << offset_bits) | offset

page_table = {0: 5, 1: 9, 2: 7}
print(hex(translate(0x2050, page_table)))  # -> 0x7050

10) Virtual Memory & Page Replacement Concepts + Code

Virtual memory lets processes run with only part of their address space resident in RAM, via demand paging.

Page fault handling: trap → validate the reference → locate the page on disk → load it into a free frame or evict a victim → update the page table → restart the faulting instruction.

PolicyRuleNotes
FIFOEvict the oldest loaded pageSimple, but can exhibit Belady's anomaly (more frames → more faults)
LRUEvict the least-recently-used pageGood approximation of optimal, but costly to implement exactly
OptimalEvict the page used farthest in the futureTheoretical benchmark only — needs future knowledge
Clock / Second-chanceUse a reference bit to approximate LRU cheaplyPractical choice in real systems
Worked example — FIFO with 3 frames: reference string 1 2 3 4 1 2 5.
1,2,3 load into empty frames (3 faults). 4 evicts 1 (fault). 1 faults again, evicts 2. 2 faults again, evicts 3. 5 faults, evicts 4.
Total faults = 7 out of 7 references — every reference after the frames fill causes a fault here, illustrating a weak reference pattern for FIFO.
LRU page replacement simulatorPython
def lru(pages, n_frames):
    frames = []
    faults = 0
    for p in pages:
        if p in frames:
            frames.remove(p)     # move to "most recently used" end
            frames.append(p)
        else:
            faults += 1
            if len(frames) == n_frames:
                frames.pop(0)     # evict least-recently-used (front)
            frames.append(p)
    return faults

print(lru([1,2,3,4,1,2,5], 3))  # -> 6 faults with LRU

Thrashing: excessive page faulting drives CPU utilization down because most time is spent swapping pages in/out rather than executing. Mitigate by lowering the multiprogramming level, or using the working-set model / page-fault-frequency control to give each process enough frames.

11) File System & I/O Concepts + Code

File systems map logical files to physical blocks and maintain metadata such as size, owner, permissions, and timestamps.

  • Allocation methods: contiguous, linked, indexed (e.g. inodes with direct/indirect blocks).
  • Directory structures: single-level, two-level, tree, acyclic graph.
  • Access control: Unix permissions (rwx for owner/group/other), ACLs for finer-grained control.
  • I/O methods: programmed I/O (CPU polls), interrupt-driven I/O (device signals completion), DMA (device transfers directly to memory, freeing the CPU).

Kernel buffering and caching improve throughput by reducing device wait time and batching small operations into larger ones.

Basic file I/O via syscallsC
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    int fd = open("notes.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) return 1;

    const char *msg = "paging beats segmentation for fragmentation\n";
    write(fd, msg, strlen(msg));  // buffered by the kernel, flushed later
    close(fd);                    // releases the file descriptor
    return 0;
}

12) Disk Scheduling Concepts + Worked Example

AlgorithmIdea
FCFSServe requests in arrival order
SSTFServe the closest request to the current head position next
SCANSweep head in one direction servicing requests, reverse at the end ("elevator")
C-SCANLike SCAN, but jumps back to the start after reaching the end, servicing only one direction — more uniform wait times
Worked example — SSTF: head starts at cylinder 50, requests = [98, 183, 37, 122, 14, 124, 65, 67].
Nearest to 50 is 65 → 67 → 37 → 14 → 98 → 122 → 124 → 183.
Total head movement = |50-65| + |65-67| + |67-37| + |37-14| + |14-98| + |98-122| + |122-124| + |124-183| = 15+2+30+23+84+24+2+59 = 239 cylinders.
SSTF total seek distancePython
def sstf(start, requests):
    requests = list(requests)
    head = start
    total = 0
    order = []
    while requests:
        nxt = min(requests, key=lambda r: abs(r - head))
        total += abs(nxt - head)
        head = nxt
        order.append(nxt)
        requests.remove(nxt)
    return order, total

print(sstf(50, [98,183,37,122,14,124,65,67]))

13) High-Frequency Interview Q&A

Q: Why are system calls slower than normal function calls?
A: They require a user-to-kernel mode switch, argument validation, and possibly scheduling or interrupt handling — a normal call is just a jump on the same stack.
Q: Why are threads considered lightweight?
A: They share the process's address space, file descriptors, and other resources, so creation and context-switch overhead is lower than for a full process.
Q: Semaphore vs Mutex?
A: Mutex is an ownership-based exclusive lock (only the locker unlocks); semaphore is a more general signaling/counting primitive and often allows a non-owner to signal it.
Q: Starvation vs Deadlock?
A: Starvation is indefinite postponement of one process (others keep progressing); deadlock is circular waiting where none of the involved processes can proceed at all.
Q: What is a zombie process?
A: A terminated child whose exit status hasn't been collected by its parent yet (parent hasn't called wait()); its PCB lingers until reaped.
Q: What causes priority inversion?
A: A low-priority thread holds a lock needed by a high-priority thread, while an unrelated medium-priority thread preempts the low-priority one and runs instead — inverting the intended priority order. Mitigate with priority inheritance.
Q: What's the difference between a hard link and a symbolic link?
A: A hard link is another directory entry pointing to the same inode (same data, indistinguishable from the "original"); a symlink is a separate file containing a path, which breaks if the target moves.
Q: Why does fork() return twice?
A: It creates a near-identical copy of the calling process; execution resumes in both parent and child right after the call, distinguished only by the return value (0 in child, child's PID in parent, negative on error).

14) Common Pitfalls to Avoid

  • Confusing concurrency with parallelism — concurrency is about structure (interleaved progress), parallelism is about execution (simultaneous on multiple cores). You can have one without the other.
  • Saying "semaphore = mutex" — they overlap in use but differ in ownership semantics and intended purpose (exclusion vs signaling).
  • Forgetting to release locks on early return / exception paths — a common source of deadlock in real code; always match every lock() with an unlock() on every path.
  • Assuming more page frames always means fewer faults — Belady's anomaly shows FIFO can violate this intuition.
  • Ignoring the ABA problem in lock-free code — a value changing from A to B and back to A can fool a naive compare-and-swap check.
  • Not reaping child processes — leads to zombie accumulation until the parent exits or calls wait().
