DBMS Complete Revision Guide

For interviews, always answer in this pattern: definition -> why needed -> example -> trade-off. This page is structured in that format to help both tests and viva rounds.

Syllabus coverage Theory + practical SQL System design links Interview framing

1) DBMS Fundamentals & Architecture

DBMS is software that stores and manages data while ensuring consistency, concurrency, security, and recoverability.

  • Why DBMS over file system: avoids redundancy, inconsistent updates, weak security, and difficult concurrent access.
  • Components: query processor, storage manager, transaction manager, lock manager, recovery manager, buffer manager.
  • Data dictionary/catalog: metadata about schemas, constraints, indexes, users, permissions.
Exam angle: Differentiate DBMS and RDBMS clearly. RDBMS enforces relational model principles (tables, keys, constraints, SQL).

2) Data Models & 3-Schema Architecture

ModelDescriptionUse case
HierarchicalTree-like parent-childLegacy systems, strict hierarchy
NetworkGraph-based, many-to-many linksComplex relationship legacy data
RelationalTables + keys + set operationsGeneral transactional apps
Object-relationalRelational + object featuresComplex domain models

3-schema architecture:

  • External level: user-specific views.
  • Conceptual level: global logical schema.
  • Internal level: physical storage details.

Data independence: logical independence and physical independence are classic exam definitions.

3) ER Model & Mapping to Tables

ER modeling transforms real-world requirements into structured schema.

  • Entity: object (Student, Course).
  • Attribute: property (name, roll_no).
  • Relationship: association (Enrolls).
  • Cardinality: 1:1, 1:N, M:N.
  • Participation: total or partial.
  • Weak entity: depends on owner entity and partial key.

Mapping rules: entity -> table, M:N relationship -> junction table, multivalued attribute -> separate table, composite attribute -> atomic columns.

4) Keys, Constraints, Dependencies

Key taxonomy: super key, candidate key, primary key, alternate key, foreign key, composite key, surrogate key.

Constraints:

  • Domain constraint: value type/range.
  • Entity integrity: primary key cannot be NULL.
  • Referential integrity: foreign key must reference existing parent (or null if allowed).
  • User-defined/business constraints: salary > 0, start_date < end_date.

Functional dependency (FD): X -> Y means X determines Y. Candidate key is minimal determinant for all attributes.

5) Normalization (1NF, 2NF, 3NF, BCNF, 4NF, 5NF)

Normalization removes anomalies and redundant storage by decomposition.

Normal formConditionFixes
1NFAtomic attributes, no repeating groupsRepeating/multi-valued fields
2NF1NF + no partial dependency on composite keyPartial dependency anomalies
3NF2NF + no transitive dependency (non-key -> non-key)Transitive anomalies
BCNFEvery determinant is a candidate keyStronger FD anomalies
4NFNo non-trivial multivalued dependencyMVD-induced redundancy
5NFNo non-trivial join dependencyJoin dependency anomalies

Decomposition quality checks: lossless join and dependency preservation are standard exam points.

Interview answer pattern: “I normalize to 3NF/BCNF for consistency, then denormalize selected areas for read-heavy workloads.”

6) Relational Algebra & Relational Calculus

Relational algebra operators: selection (sigma), projection (pi), union, set difference, cartesian product, rename, join, division.

Joins: theta join, equi join, natural join, inner/outer join, semi join, anti join.

Relational calculus:

  • Tuple relational calculus (TRC)
  • Domain relational calculus (DRC)

Important property: relational algebra is procedural, relational calculus is non-procedural.

7) SQL Core (DDL, DML, DCL, TCL)

DDL: CREATE, ALTER, DROP, TRUNCATE.

DML: SELECT, INSERT, UPDATE, DELETE, MERGE.

DCL: GRANT, REVOKE.

TCL: COMMIT, ROLLBACK, SAVEPOINT.

  • WHERE vs HAVING: row filter vs group filter.
  • GROUP BY rule: all selected non-aggregated columns must be grouped.
  • NULL logic: use IS NULL/IS NOT NULL, avoid = NULL.

8) Advanced SQL (CTE, Windows, Views, Procedures, Triggers)

CTE: readable multi-step query blocks; recursive CTE for hierarchy/tree traversal.

Window functions: ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD, running totals.

Views: virtual tables, help abstraction and security; materialized views store computed data physically.

Stored procedures: server-side procedural routines; good for encapsulating data logic.

Triggers: automatic actions on INSERT/UPDATE/DELETE; use carefully to avoid hidden side effects.

NeedPreferred SQL pattern
Top N per groupROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)
Find missing childrenNOT EXISTS or left anti join pattern
Hierarchy traversalRecursive CTE
Slow aggregate refreshMaterialized view + scheduled refresh

9) Indexing & File Organization

Indexes trade write overhead for read speed.

  • B+ tree index: balanced, supports equality and range queries.
  • Hash index: fast point lookups, poor for range scans.
  • Clustered index: table data physically ordered by key (one per table).
  • Non-clustered index: separate structure with row pointers.
  • Covering index: query served fully from index without table lookup.
  • Composite index: follows leftmost-prefix rule.

File organizations: heap file, sequential file, hash file.

Index pitfall: Too many indexes can significantly slow INSERT/UPDATE/DELETE.

10) Query Processing & Optimization

Query flow: parse -> rewrite -> optimize -> execute.

  • Parser: validates syntax/semantics.
  • Rewriter: applies equivalence rules (predicate pushdown, projection pushdown).
  • Optimizer: cost-based plan choice using statistics.
  • Executor: runs physical operators.
Join strategyBest fitRisk
Nested loopSmall outer + indexed innerVery slow without index
Hash joinLarge equality joinsMemory pressure/spill
Sort-mergeSorted inputs or range logicSort cost if unsorted

EXPLAIN checklist: full table scans, wrong cardinality estimates, missing indexes, expensive sort/hash spill.

11) Transactions, ACID, Schedules & Serializability

Transaction is a unit of work that must preserve correctness under failures and concurrency.

ACID: Atomicity, Consistency, Isolation, Durability.

Schedule types: serial, non-serial, conflict-serializable, view-serializable.

Recoverability classes: recoverable schedule, cascadeless schedule, strict schedule.

  • Conflict equivalence: based on read-write/write-read/write-write conflicts.
  • Precedence graph: acyclic graph implies conflict serializability.

12) Concurrency Control & Isolation Levels

Common anomalies: dirty read, non-repeatable read, phantom read, lost update, dirty write.

IsolationDirty readNon-repeatablePhantom
Read UncommittedYesYesYes
Read CommittedNoYesYes
Repeatable ReadNoNoPossible (engine-specific)
SerializableNoNoNo

Mechanisms:

  • Lock-based: shared/exclusive/intention locks, 2PL, strict 2PL.
  • Timestamp ordering: enforce global transaction order by timestamps.
  • MVCC: multiple row versions; readers don’t block writers in many engines.
  • Optimistic concurrency: validate at commit; good when conflicts are rare.

13) Deadlocks, Starvation, Livelock

Deadlock: cyclic waiting between transactions/resources.

Coffman conditions: mutual exclusion, hold-and-wait, no preemption, circular wait.

ProblemMeaningMitigation
DeadlockCircular waitDetection + victim rollback, lock ordering
StarvationOne txn waits indefinitelyFair scheduling, aging
LivelockConstant retries, no progressRandom backoff, retry caps

Deadlock handling: prevention, avoidance, detection and recovery (most practical DBs use detection+recovery).

14) Recovery, WAL, Checkpointing

Goal: return DB to consistent state after crash/media/system failure.

  • WAL rule: log record reaches stable storage before corresponding data page.
  • ARIES ideas: analysis, redo, undo phases with log sequence numbers (LSN).
  • Checkpoint: bounds amount of log scanning during recovery.
  • Undo/Redo matrix: depends on no-force/steal policy combinations.
Interview tip: Durability is largely achieved via WAL + fsync + replication, not only by writing table pages immediately.

15) Buffer Manager, Pages, and Disk Internals

DBMS works page-by-page, not row-by-row at disk level.

  • Page: fixed-size block (e.g., 8KB, 16KB).
  • Buffer pool: in-memory cache of pages.
  • Replacement policies: LRU, clock variants, MRU in specific workloads.
  • Pin/unpin: prevents eviction of in-use pages.
  • Dirty page: modified page requiring flush.

Disk-aware design: sequential I/O is cheaper than random I/O; optimizer and index design exploit this.

16) Distributed DBMS, Replication, Sharding

Replication: copies same data across nodes for availability/read scaling.

Sharding/partitioning: split data across nodes by key/range/hash.

  • Horizontal partitioning: rows divided by predicate/key.
  • Vertical partitioning: columns split across tables/services.
  • 2PC: distributed transaction protocol (prepare/commit); consistency vs latency trade-off.
  • Consensus links: leader election and log agreement often rely on raft/paxos-style systems.

Common challenge: cross-shard joins and transactions are expensive.

CAP theorem: under network partition, choose consistency or availability (cannot guarantee both fully).

BASE: Basically Available, Soft state, Eventual consistency.

Interview framing: NoSQL is not “better than SQL”; it is better for specific access patterns and scale constraints.

18) DB Security, Authorization, Auditing

  • Authentication: verifies identity.
  • Authorization: controls what identity can do (RBAC/ABAC).
  • Encryption: at rest (disk), in transit (TLS), and field-level where needed.
  • Auditing: track who changed what and when.
  • Least privilege: grant minimal required permissions.

SQL injection prevention: parameterized queries/prepared statements, never string-concatenate user inputs into SQL.

19) Backup, Restore, and High Availability

Backup types: full, differential, incremental, snapshot-based.

  • RPO (Recovery Point Objective): acceptable data loss window.
  • RTO (Recovery Time Objective): acceptable restoration time.
  • PITR: point-in-time recovery using base backup + WAL logs.
  • HA setup: primary-replica, failover automation, health checks.

Best practice: backups are useful only if restore drills are tested regularly.

21) High-Frequency Interview Q&A

Q: Why is normalization needed?
A: It reduces redundancy and anomalies; improves consistency and maintainability.
Q: 3NF vs BCNF?
A: BCNF is stricter; every determinant must be a candidate key.
Q: Clustered vs non-clustered index?
A: Clustered determines physical row order; non-clustered is separate pointer structure.
Q: Why can phantom reads occur?
A: Range query re-executed sees newly inserted/deleted rows matching predicate.
Q: Why is WAL important?
A: Ensures redo/undo information survives crash before dirty pages flush.
Q: Repeatable Read vs Serializable?
A: Serializable prevents phantoms and emulates serial execution, at higher concurrency cost.
Q: SQL join faster with FK index?
A: Yes, because lookup on referenced rows avoids full scans for join/filter paths.
Q: What is denormalization and when to use it?
A: Intentional redundancy to reduce joins in read-heavy paths after measuring bottlenecks.

22) Must-Do Numericals & Cheatsheet

For tests, practice these repeatedly:

  • FD closure and candidate key finding (X+ computation).
  • Normalization decomposition with lossless/dependency-preserving proof.
  • Conflict serializability using precedence graph cycle detection.
  • Recoverable/cascadeless/strict schedule classification.
  • Transaction anomaly identification under each isolation level.
  • Index selection reasoning for query workload.

Memory line: DDL defines, DML manipulates, TCL controls transaction, DCL controls permission.
